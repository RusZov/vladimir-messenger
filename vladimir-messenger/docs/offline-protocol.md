# Протокол офлайн-работы

## Обзор

Владимир поддерживает работу без интернета через два механизма:
1. **Локальная сеть (LAN)** — UDP discovery + TCP transfer
2. **Bluetooth LE Mesh** — BLE GATT для связи на расстоянии до 10м

## LAN режим

### Discovery протокол

Каждый узел периодически (каждые 5 секунд) отправляет UDP широковещательное сообщение:

```json
{
    "type": "discovery",
    "peer_id": "уникальный_id_узла",
    "public_key": "base64_публичный_ключ",
    "tcp_port": 5001,
    "timestamp": unix_timestamp
}
```

**Параметры:**
- Порт UDP: 5000
- Адрес: `<broadcast>` (255.255.255.255)
- Интервал: 5 секунд
- Таймаут ответа: 1 секунда

### Процесс обнаружения

```
Узел A                          Узел B
   |                               |
   |--- UDP Broadcast ----------->|
   |                               |
   |<-- UDP Unicast Response -----|
   |                               |
   |--- TCP Connection Request -->|
   |                               |
   |<== Encrypted Message =======>|
```

### Формат TCP сообщения

```
[4 bytes: длина][JSON данные]
```

Пример JSON:
```json
{
    "id": "uuid сообщения",
    "type": "encrypted",
    "nonce": "base64",
    "ciphertext": "base64",
    "sender_id": "id отправителя",
    "sender_public_key": "base64",
    "timestamp": unix_timestamp
}
```

### Обработка коллизий

Если несколько узлов отвечают одновременно:
1. Каждый ответ обрабатывается независимо
2. Дубликаты сообщений отфильтровываются по `message.id`
3. Информация о пире обновляется по последнему timestamp

## BLE Mesh режим

### Топология сети

```
┌─────────┐     ┌─────────┐     ┌─────────┐
│  Узел A │────▶│  Узел B │────▶│  Узел C │
│(отправ.)│  1  │(релей)  │  2  │(получ.) │
└─────────┘     └─────────┘     └─────────┘
```

### Формат BLE пакета

Максимальный размер MTU: 20 байт (без negotiations)
Используется фрагментация для больших сообщений.

**Header (4 байта):**
```
[Type: 1 byte][Flags: 1 byte][Length: 2 bytes]
```

**Payload (до 16 байт):**
Фрагмент данных сообщения

### Процесс ретрансляции

1. **Прямая передача** (если получатель в зоне видимости):
   - Подключение к устройству
   - Запись в TX characteristic
   - Ожидание ACK

2. **Ретрансляция** (если получатель вне зоны):
   - Поиск доступных релеи
   - Отправка с флагом `relay_for: target_id`
   - Увеличение счётчика hops
   - Сохранение в локальной очереди

### TTL и экспирация

- Максимум прыжков: 3
- Время жизни сообщения: 5 минут
- После истечения TTL сообщение удаляется

```python
if hops >= MAX_HOPS:
    discard_message()
    
if time.time() - queued_at > MESSAGE_TTL:
    cleanup_expired_messages()
```

## Mesh Queue

### Структура очереди

```python
mesh_messages = {
    "peer_id": [
        {
            "message": {...},
            "queued_at": timestamp,
            "hops": 0,
            "retry_count": 0
        }
    ]
}
```

### Процесс доставки

1. Сообщение ставится в очередь если получатель недоступен
2. Периодически (каждую минуту) проверяется доступность получателя
3. При появлении — попытка отправки
4. После успешной отправки — удаление из очереди
5. После 5 минут — принудительное удаление

### Статистика

| Метрика | Значение |
|---------|----------|
| Max queue size | Неограничено (RAM) |
| TTL | 300 секунд |
| Retry interval | 60 секунд |
| Max retries | Неограничено (в пределах TTL) |

## Обработка конфликтов

### Сценарий: Несколько путей доставки

```
      ┌───▶ Relay 1 ───┐
Src ──┤                ├──▶ Dst
      └───▶ Relay 2 ───┘
```

**Решение:**
- Первое доставленное сообщение принимается
- Дубликаты отбрасываются по `message.id`
- Отправитель получает ACK только один раз

### Сценарий: Разрыв соединения во время передачи

**Решение:**
- Сообщение остаётся в очереди
- Попытка повторной отправки при восстановлении
- Частично переданные данные отбрасываются

## Безопасность офлайн-режима

### Угрозы

1. **Спуфинг пира** — злоумышленник выдаёт себя за другого
   - Защита: проверка публичного ключа

2. **Replay атака** — перехват и повторная отправка сообщения
   - Защита: уникальные nonce, timestamps

3. **Mesh poisoning** — введение ложных路由ов
   - Защита: проверка подписей (будущая версия)

### Рекомендации

- Всегда проверяйте публичные ключи контактов
- Используйте QR-коды для первичного обмена
- В чувствительных сценариях ограничьте доверенные узлы

## Производительность

### Бенчмарки (ожидаемые)

| Операция | Время |
|----------|-------|
| UDP Discovery | < 100ms |
| TCP соединение | < 500ms |
| Шифрование сообщения (1KB) | < 10ms |
| BLE передача (20 байт) | < 50ms |
| Mesh ретрансляция (1 hop) | < 200ms |

### Оптимизации

- Кэширование общих секретов DH
- Lazy connection establishment
- Batch обработка discovery ответов
